### 🎼 五线谱保存格式：为何 SVG 是唯一解？

你的核心需求是 **“在 MIDI/WAV/MP3 播放时，自动对齐并标注在五线谱上的位置”**。这要求五线谱不仅是一个静态图像，更是一个**可交互的、带坐标信息的矢量图形**。

*   **PNG / JPG (位图)**：**不可行**。它们是像素图像，无法获取音符的精确坐标，缩放会模糊，完全无法实现精准的“对齐标注”。
*   **PDF (矢量文档)**：**不适合交互**。PDF 是优秀的打印和分享格式，但它是一个封闭的文档容器，程序很难在播放时实时定位到 PDF 内部的某个音符并叠加高亮标记。
*   **SVG (可缩放矢量图形)**：**唯一正确选择**。SVG 基于 XML，每个音符、谱号、小节线都是独立的、带坐标的图形元素。你的程序可以：
    *   **精准定位**：轻松获取任一音符在乐谱上的精确坐标。
    *   **实时标注**：在播放时，根据时间轴数据，在对应音符位置动态绘制高亮框或标记。
    *   **无损缩放**：在任何分辨率下都清晰，适合各种屏幕。
    *   **动态交互**：甚至可以改变音符颜色、添加动画等。

市场上已有的跟弹软件（如 SheetViewer）也明确强调其使用 **MusicXML 矢量五线谱**，并指出“**比 PDF 或图片更清晰、可无限缩放**”，这间接印证了矢量格式对于交互式乐谱的必要性。

### 🎯 核心原因：两种格式的“世界观”不同

你可以把 MIDI 看作一份**演奏指令**，而 MusicXML 是一份**出版乐谱**。

*   **MIDI 只关心“怎么响”**：它记录的是哪个音在何时以多大力被按下和松开。它本质上是一套面向合成器的**播放指令集**，类似于钢琴卷帘（Piano Roll），不关心乐谱长什么样。
*   **MusicXML 关心“怎么看”**：它旨在完整记录一份**印刷乐谱**的所有信息，包括音符、记谱法、排版布局，甚至是为了“看起来专业”而存在的符号。

因此，MusicXML → MIDI 是一个**信息降维**的过程：大量为“人类阅读”而存在的视觉和符号信息，在 MIDI 的“播放指令”世界里是**完全多余甚至无法表达**的，于是被直接丢弃。

### 📉 转换中具体会“丢”掉什么？

从 MusicXML 转换为 MIDI 时，以下类别的信息会全部或大部分丢失，且无法从 MIDI 中恢复：

*   **记谱与符号**：连音线（Slurs）、歌词、力度记号（p, mf, f）、演奏法（Articulations）、装饰音、反复记号、和弦符号、速度标记文字等。
*   **布局与排版**：谱号变化、拍号显示、小节线类型、音符的符干方向、符杠分组、页面边距、字体设置等所有**视觉布局信息**。
*   **音符“拼写”**：例如，一个音符在乐谱上可能记作 **C♭**，但在 MIDI 中它只是一个音高数值，无法区分它应该显示为 C♭ 还是 B♮。

### 🔄 从 MIDI 回到 MusicXML：一个“重新猜测”的过程

当你把 MIDI 文件再转回 MusicXML 时，转换工具（如 music21 或 MuseScore）面对的是一堆没有乐谱意义的“音符事件”。它必须**猜测**如何将这些事件组织成一份合理的乐谱。

这意味着，即使原始 MusicXML 中的**音高、时值、力度**等核心演奏信息在 MIDI 中得以保留，恢复出的 MusicXML 也是**重新推断和排版**的结果，与原始文件在结构上必然存在差异。例如：

*   **休止符的“发明”**：MIDI 本身没有休止符的概念，只有“没有音符”的空白。工具需要根据音符间的空隙**推断**这里应该放一个八分休止符还是四分休止符。
*   **声部与符杠的重新分配**：工具需要猜测哪些音符属于同一个声部，以及符杠应该如何分组，这常常与原始乐谱的排版意图不同。
*   **量化处理**：如果原始演奏在时间上有微小的人性化偏差，工具在导入时可能会将音符**量化**到最近的节拍网格上，这会改变精确的时值。

### ⚠️ 补充说明：反向转换的情况

反过来，从 **MIDI → MusicXML** 则是一个**信息增维**的过程。工具需要为原始的演奏数据**添加**乐谱结构（如小节线、调号、拍号），这个添加过程充满了猜测，因此同样不会得到与某个假想的“原始 MusicXML”完全一致的文件。

### 💎 对你项目的启示

在你的转换程序设计中，需要明确：**MusicXML → MIDI 是有损的，MIDI → MusicXML 是推断性的。** 因此，你的程序架构应当**始终以 MusicXML（或等效的内部结构，如 music21 的 `Stream` 对象）作为信息的“主副本”**。

1.  **核心数据源**：所有乐谱信息（包括为播放同步所需的音符坐标、布局数据）都应以 MusicXML 或 `Stream` 对象为准来保存和操作。
2.  **MIDI 的角色**：MIDI 应被视作一个**面向播放的“导出产物”**，用于驱动音频渲染（如通过 FluidSynth 生成 WAV）。它不负责保存乐谱的完整信息。
3.  **同步逻辑**：你之前构想的“播放时对齐标注”，其**时间轴数据**应基于 MusicXML 中的音符时长来计算，而不是依赖 MIDI 中的时间戳（因为 MIDI 时间可能因量化或渲染设置而与乐谱时值有偏差）。这样，无论播放的是原始 MIDI 还是渲染后的 WAV/MP3，你都能用一套统一的、源自乐谱的时间轴来驱动 SVG 上的高亮标注。


MuseScore 打开 MusicXML 时**并非将其转换为 SVG**，播放时的高亮也**不是在 SVG 上实现的**。MuseScore 的内部机制与你的项目架构有本质区别，下面来详细说明。

### 🎼 MusicXML 的呈现：内部实时渲染，而非 SVG 转换

MuseScore 打开 MusicXML 文件时，会将其解析并转换为自己的**内部乐谱数据结构**，而不是转成 SVG 来显示。

- **内部表示**：MusicXML 被解析后，会映射到 MuseScore 的 `Score` 对象。这个对象以树状结构组织乐谱，包含 `Measure`（小节）、`Segment`（片段）、`Chord`（和弦）等元素，并记录了每个元素的**布局偏移（Layout Offset）**和**锚点位置（Anchor Position）**。
- **屏幕渲染**：MuseScore 使用 **Qt 的 QPainter** 图形引擎，将内部的 `Score` 对象**实时绘制**到屏幕上。这是一个直接的矢量绘制过程，**不涉及先生成 SVG 文件再显示的步骤**。
- **SVG 的角色**：SVG 在 MuseScore 中主要用于**导出**，而不是显示。你可以通过菜单或命令行，将乐谱**导出**为 SVG 文件用于其他用途，但这与打开 MusicXML 后的显示流程是分开的。

### ✨ 播放高亮：修改内部元素颜色，而非操作 SVG

MuseScore 播放时的音符高亮，是通过**直接修改内部 `Element`（元素）对象的颜色状态**来实现的，同样与 SVG 无关。

1. **定位与标记**：播放引擎根据当前 MIDI tick 位置，通过 `Seq::seek()` 找到对应的音符，并调用 `addRefresh()` 将其标记为“高亮状态”。
2. **重绘**：标记后触发界面刷新，调用 `ScoreView::paint()` 进行重绘。
3. **颜色覆盖**：在重绘时，`QPainter` 会读取每个 `Element` 的当前颜色。对于被标记为高亮的元素，其颜色会被设置为一个**不同的高亮颜色**（如蓝色），从而在视觉上“点亮”该音符。
4. **恢复**：播放完毕后，音符的颜色状态被重置，再次刷新该区域，音符就恢复了正常颜色。

### 💎 对你的项目有什么启示？

MuseScore 的这套机制和你的项目目标（在 SVG 上实现高亮）是两种不同的技术路径：

| 特性 | MuseScore (原生应用) | 你的项目 (Web/跨平台应用) |
| :--- | :--- | :--- |
| **乐谱显示** | 内部 `Score` 对象 + `QPainter` 实时绘制 | 预生成的 **SVG** 文件 |
| **高亮实现** | 修改内部 `Element` 的颜色属性并重绘 | 通过 DOM 操作，**动态修改 SVG 元素的样式**（如 `fill` 颜色） |
| **优势** | 高度集成，性能可控，适合复杂的桌面端排版与交互 | 格式开放，易于在 Web 环境中嵌入和交互，**矢量缩放无损** |

所以，你的项目采用 **“SVG + DOM 操作”** 来实现高亮，在技术上是完全可行且更符合 Web 应用场景的。你需要做的，就是在生成 SVG 时，为每个音符元素附加一个**唯一标识符（ID）**，并在播放时通过时间轴映射表，用 JavaScript 动态改变对应 SVG 元素的样式（如 `fill` 或 `stroke`）来实现高亮。
